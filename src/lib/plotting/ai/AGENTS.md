# AI plotting rules

- Plotting AI prompts live as `.txt` templates in `src/lib/plotting/ai/templates/`, imported with `?raw`. Why: prompts stay editable without touching code.
- «Нарисовать по заданию» for line/plane: stage 1 returns `reasoning` + explicit `drawPlan` + `sceneType`; stage 2 gets only `drawPlan` and fills a reduced draft (`generate-draw-line.txt` / `generate-draw-plane.txt`), which `draft-line.ts` / `draft-plane.ts` expand into the full scene (colors, widths, steps, ids are set in code, never by the model). Prefer tool-side relations (intersection / onGraph / graphPoint) over model-computed coordinates; `drawPlan` must not carry coordinates of dependent points, and `draft-plane.ts` converts a `coords` point that is the sole crossing of two explicit graphs into `intersection`. Axis limits are chosen in stage 1 by the task's needs (what is given vs what the student must find — the latter is not drawn), aim for a near-square field, and code guarantees ≥6 grid cells per axis (`niceStep`, `pickStep`). Space still uses the old full-schema path. Why: the model decides only content; the app owns technical and visual values.
- The `/workspace` "generate by text" flow uses its own scenario `task` (`task-analyze.txt`, `task-generate-plane.txt`, `task-generate-line.txt`); the main page `draw` prompts stay separate. Stage 1 receives task text + wishes and returns a verbal plan split into ПОСТРОИТЬ / ПОДПИСАТЬ; stage 2 receives only the plan and fills the reduced draft, with `minimalLabels` so unlabeled points hide coordinates. Why: the editor shows only what the task explicitly states and never hints the answer.
- Technical prompt instructions (draft JSON schemas, plan rules, JSON output rules) live only in shared `tech-*.txt` / `json-output-rules.txt` templates, injected by `prompts.ts` (`withTechBlocks`); scenario templates contain only role, input and label policy. Why: a schema change must reach every scenario at once.
- All analysis builders and the concrete-variant planning builder use shared `analysis-precision-rules.txt` and `analysis-structure-rules.txt`; the latter also defines the verbal plan format via `tech-plan-rules.txt`. Why: every scenario lists future constructions consistently without changing JSON contracts or choosing variant numbers prematurely.
- "Аналог по скриншоту" (`ai/analog-task.ts`, `AnalogTaskDialog`): stage 1 returns only a template (preserved/varied rules, answer rule, visibility, figure slots with fixed placement/optionIndex); stage 2 produces N concrete variants with plans in one call (keeps variants distinct), slots enforced by `parseAnalogVariant`; stage 3 builds each variant's figures via draft expanders; `lib/workspace/analog-block.ts` turns each into a block. Why: concrete numbers are chosen only once per variant, and image placement never depends on the model guessing.
- Task-generation figure branches also accept `chart`; stage 2 fixes concrete data in the plan, stage 3 uses the shared `tech-chart-json.txt` schema and `validateAiChartJson`. Why: request and screenshot tasks support the same charts and initial defaults as plotting.
- "Задание с чертежом по запросу" reuses the analog flow: only stage 1 differs (`request-task-analyze.txt`, `analyzeRequestTask`) and returns the same template; stages 2–3 run without an image (`source: "request"`). Why: one pipeline for both entry points.
