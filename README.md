# Math graphics

MVP: AI Infographic Generator

Цель

Создать прототип приложения, которое превращает исходный текст или тему в готовую инфографику через несколько последовательных этапов работы ИИ.

Это отладочный прототип, созданный для того, чтобы пользователь мог на любом этапе контролировать запросы к LLM и максимально точечно влиять на результат.

Ключевая идея MVP:

пользователь может вмешаться после каждого этапа;

Все промпты видны и доступны для отладки

генерация изображения не происходит напрямую из текста;

между анализом текста и рисованием существует промежуточный этап создания дизайн-брифа (промпта для рисующей модели);

Имеются вспомогательные описания стилей расположения информации и цветового оформления, из которых собирается общая инструкция

пользователь может увидеть wireframe будущей инфографики до генерации изображения.





Вншний и внутренний дизайн

Все панели и кнопки взаимодействия с материалом от пользователя – слева, всё, что произведено на этапе – справа.




Каждый из промптов, описанных далее, создаётся в отдельном текстовом файле. Этот текст выводится по умолчанию в окошки, описанные далее, и для обращения к LLM берётся уже оттуда.

Шаг 2. Анализ содержания

В него внеси описанную выше задачу, но пропиши чётко структуру “текст инструкции + контент, загруженный пользователем” или “текст инстуркции + тема”. Поскольку это две разные инструкции, сделай под это две разные переменные; приложение должно верно выбирать вариант запроса в зависимости от того, что предоставил пользователь; инструкция собирается из базового промпта, пожеланий пользователя и списка доступных инфографик с кратким описанием. Выход

В результате этого запроса модель должна отдать строго json структуру, состоящую из двух частей:

1. структурированный текст, который должен оказаться на инфографике. Это финальный текст, каждый элемент которого будет размещён на инфографике, в следующих шагах не будет добавляться ничего и ничего убираться из него тоже не будет.

Разрешены:

Markdown для заголовков и таблиц

LaTeX для формул

Нужно добавить проверку того, что модель возвращает верную структуру без лишних символов и дополнительных комментариев

2. рекомендуемый стиль инфографики; из списка, приложенного к инструкции, модель выбирает тот, который кажется ей наиболее подходящим для рассматриваемой инфографики. Список берётся из хранилища, встроенного в приложение.

После парсинга ответа модели полученный от неё текст отображается на правой части экрана с корректно отображающейся разметкой. Текст доступен пользователю для редактирования на случай, если он хочет что-то добавить или убрать. Также справа появляется кнопка перегенерировать.

В левой части экрана на одном уровне появляются два выпадающие списка: со стилями инфографик и с цветовой+шрифтовой палитрой. В выпадашке для стилей установлен тот, который определён моделью; о цветах+шрифтах ниже.

Под этими выпадашками справа кнопка просмотра промпта создания инструкций для рисования (всё как в предыдущем случае про анализ; что конкретно это за промпт, рассказано ниже); также рядом выпадашка со списком моделей и кнопка “создать дизайн-бриф” по которой запускается шаг 3 (см. ниже)

 Возможно, структура и представление стилей будут меняться, пока что это будет простая json-структура в отедльном файле с названием, кратким описанием-пояснением, и набором правил дизайна (т.е. Пока что 3 поля).

Шаг 3. Создание дизайн-брифа для рисующей модели

ВАЖНО:

На этом этапе изображение ещё НЕ создаётся. Вместо этого модель должна создать подробный промпт, который далее будет передан модели, ответственной за рисование.

Для создания дизайн-брифа ИИ получает общую инструкцию, составленную из следующих частей:

Выжимку содержания, полученную на шаге анализа и, возможно, отредактированную пользователем. Это единственный источник содержания, которое нельзя изменять.

Общую часть инструкции, которая описывает смысл действия и правила группировки и структурирования информации, независимо от стиля (для этой инструкции нужен отдельный текстовый файл) – именно эта часть будет отображаться и редактироваться по кнопке, расположенной под выпадашками для стиля инфографики и цвета+шрифта

Выбранный стиль инфографики со всем списком правил дизайна (берётся со вспомогательной страницы, в которой содержится либо загруженный из джейсон-структуры текст, либо созданный/отредактированный пользователем при заходе на вспомогательную страницу).

Дополнительные настройки дизайна (цвета и шрифтов из второй выпадашки) со списком инструкций для его применения. Об этом ниже

ИИ должен создать:

промпт для рисующей модели;

wireframe будущей инфографики.








Дополнительные настройки дизайна

Как и со стилями инфографики, нужна отдельная страница настройки дизайна. Должна существовать система по умолчанию

Цель

Позволить пользователю задать ключевые визуальные параметры (цветовая палитра, типографика, основные акценты), не указывая полностью каждый блок, чтобы ИИ мог «догадаться» остальное.

Структура страницы

Выбор палитры

Основной фон (цвет/тон)

Основной акцент (для важных элементов)

Второстепенный акцент (для деталей, вспомогательных элементов)

Дополнительные акценты (опционально, 1–2 цвета)

Тип визуальных градиентов/теней: flat / soft / none (для MVP оставить только flat)

Выбор шрифтов

Основной шрифт (для заголовков, body)

Дополнительный шрифт (для примеров, формул)

Начертания, которые будут использоваться (Regular / Medium / Bold / Italic)
 Можно оставить выбор лишь основных весов заголовков и body.

Правила применения акцентов

Основной акцент → заголовки, ключевые элементы

Второстепенный акцент → карточки, подписи, маркеры

Дополнительные акценты → иконки, стрелки, элементы схем

Автоподбор оттенков (если конкретный цвет не задан для блока, ИИ генерирует подходящий вариант из заданной палитры)

Опциональные параметры

Скругления карточек

Применение контуров/рамок (да/нет, цвет по умолчанию — основной акцент)

Минимальные отступы/паддинги (в процентах или условных единицах)

Рекомендации для ИИ

Модель использует эти акценты как семантические маркеры (главное/второстепенное/дополнительное)

Остальные блоки, которых нет явно в профиле, подбираются автоматически

Не задавать слишком много строгих параметров, оставляя пространство для интерпретации





2️⃣ Пример структуры JSON для хранения цвето-шрифтовых профилей

{

 "profileName": "DefaultBentoStyle",

 "background": "#FFFFFF",

 "accents": {

   "primary": "#F58220",

   "secondary": "#6C5CE7",

   "additional": ["#FCD9B0", "#DCD4F2"]

 },

 "fonts": {

   "primary": {

     "family": "Roboto",

     "weights": ["Regular", "Bold", "Black"]

   },

   "secondary": {

     "family": "Spectral",

     "weights": ["Italic", "BoldItalic", "Upright"]

   }

 },

 "usageRules": {

   "primaryAccent": ["header", "keyText", "importantIcons"],

   "secondaryAccent": ["cards", "labels", "minorIcons"],

   "additionalAccents": ["illustrations", "arrows", "misc"]

 },

 "cardStyle": {

   "borderRadius": "16px",

   "border": "optional",

   "shadow": "none"

 },

 "spacing": {

   "padding": "default",

   "interBlockGap": "default"

 },

 "notesForAI": "If a block is not explicitly assigned a color or font, the AI can select a matching accent or weight from the palette."

}

Комментарии к JSON

profileName — имя профиля.

accents — высокоуровневые акценты, не обязательно привязывать каждый к конкретному блоку.

fonts — два шрифта: основной и дополнительный для особых случаев (формулы, примеры, цитаты).

usageRules — рекомендуемое распределение акцентов; ИИ может додумать остальные.

cardStyle и spacing — минимальные обязательные визуальные параметры.

notesForAI — текстовое поле для инструкций ИИ, как «догадаться» при неполных данных.




В приложении должен быть по умолчанию установлен один базовый сохранённый профиль и на вспомогательной странице должна быть возможность сохранить новый. Сохранённые новые профили “держатся” в течение сесии и как только сохранены, включаются в выпадашку для цветов+шрифтов





Wireframe

После генерации дизайн-брифа необходимо отобразить wireframe.

Wireframe должен показывать:

расположение блоков;

Примерные размеры блоков;

связи между блоками;

наличие иллюстраций;

главный визуальный объект.

Wireframe НЕ должен содержать:

реальные цвета;

реальные шрифты;

декоративные детали.

Только структура.

Пример:

┌────────────────────┐

│ Заголовок                                 │

└────────────────────┘

┌─────────┐ ┌─────────┐

│ Факт 1           │  │ Факт 2           │

└─────────┘ └─────────┘

┌────────────────────┐

│ График                                      │

└────────────────────┘ 





Wireframe должен генерироваться на основе того же layout, который попадает в финальный промпт для рисующей модели.

То есть:

один источник истины для layout.





Формат ответа модели на этапе 3

Модель должна вернуть два независимых результата:

Result A

PromptForImageGeneration

Полный текстовый промпт для Nano Banana или аналогичной модели.

Result B

WireframeDescription

Упрощённое текстовое описание структуры инфографики.

Именно оно используется интерфейсом для визуализации wireframe.




Как и раньше, должна производиться проверка корректности структуры возвращаемого ответа модели и попытки удалить лишнее / распарсить если есть какие-то ошибки.

После получения корректного ответа в правой части приложения отображается wireframe и кнопка перегенерации, в левой части появляется окошко “доп.пожелания”; если нажимается перегенерация, что нужно прибавлять к инструкции модели ещё и доп.пожелания пользователя, если окошко не пустое;

В левой части приложения появляется третья кнопка кнопка “просмотреть промпт”, по нажатию открывается полученное PromptForImageGeneration; рядом выпадашка со списком моделей, и левее всего - кнопка “сгенерировать изображение”





Шаг 4. Генерация изображения

На этом этапе:

PromptForImageGeneration

передаётся в рисующую модель.

Получаем итоговую инфографику.

При перегенерации также проверяется содержимое окошка доп.пожеланий пользователя и добавляется к промпту, если было не пусто; доп-пожеланиям отдаётся приоритет по сравнению с промптом из PromptForImageGeneration

При этом должно быть реализовано сохранение версий, чтобы изменения на каком-то этапе не стирали бесследно предыдущие результаты; версии должны храниться либо в течение сессии, либо пока пользователь на нажмёт на особую кнопку “начать заново”. Важно, нажатие этой кнопки стирает то, что относится к конкретным созданиям инфографик, но не изменяет ни тех изменнений, что пользователь внёс в базовые промпты, ни изменений, созданных на вспомогательных страницах.

Внутренняя архитектура данных

Для упрощения дальнейшей разработки все проекты инфографики должны храниться как набор отдельных сущностей, а не как один общий объект данных.

Приложение должно поддерживать следующую структуру проекта.

SourceText (Исходный материал)

Оригинальный пользовательский ввод.

Может содержать:

исходный текст;

содержимое загруженного файла;

только тему.

После загрузки этот объект не должен автоматически изменяться системой.





ContentSummary (Выжимка содержания)

Результат этапа анализа контента.

Содержит:

учебное содержание;

определения;

правила;

примеры;

формулы;

выводы;

предупреждения;

памятки.

ContentSummary не должен содержать дизайнерских инструкций.

Это исключительно информационный слой, полученный после первого запроса к ИИ на анализ текста.








StyleSpecification (Спецификация стиля инфографики)

Описывает выбранный тип инфографики (то, что делается на доп.старице задачи стилей, см. выше).

Содержит высокоуровневую визуальную стратегию.

Примеры:

Modern Bento;

Scientific Diagram;

timeline;

School Reference Card;

Editorial Poster.

StyleSpecification описывает:

принципы композиции;

принципы визуальной иерархии;

использование иллюстраций;

степень симметрии;

плотность информации;

способ подачи учебного материала.

StyleSpecification не должен содержать конкретных цветов или названий шрифтов.





DesignProfile (Профиль оформления)

Описывает конкретную визуальную реализацию.

Выбирается отдельно от StyleSpecification.

Содержит:

систему цветов;

правила типографики;

форму карточек;

использование или отсутствие контуров;

стиль иконок;

стиль иллюстраций;

принципы отступов и расстояний.

Это то, что описано в разделе ”дополнительные настройки дизайна”





PromptForImageGeneration (Промпт для рисующей модели)

Результат этапа 3.

Создаётся на основе:

ContentSummary;

StyleSpecification;

DesignProfile.

И общей инструкции

Содержит полный промпт для передачи в модель генерации изображений.





Wireframe (Схема будущей инфографики)

Результат этапа 3.

Создаётся на основе той же логики композиции, которая используется при генерации PromptForImageGeneration.

Показывает:

иерархию блоков;

расположение блоков;

группы элементов;

области иллюстраций;

главный визуальный объект.

Не должен содержать:

финальных цветов;

шрифтов;

декоративных элементов.

Wireframe отображает только структуру.





FinalImage (Финальная инфографика)

Результат этапа 4.

Создаётся рисующей моделью на основе PromptForImageGeneration.





Правила регенерации

ВАЖНО: если изменяется какой-то параметр, то всё, что описано далее, не перегенерируется сразу. Вначале появляется предупреждающее окошко, сообщающее, что если пользователь заменит выбранный аспект, то произойдут следующие изменения (и изменения перечислены). При этом старые версии должны сохраняться (о сохранении версий сказано ранее)

Если изменяется SourceText:

Появляется возможность создать новую выжимку на основе анализа, но только по нажатию кнопки; создаётся новая версия текста.

Если изменяется ContentSummary:

пересчитывается рекомендация стиля;

пересоздаются PromptForImageGeneration;

пересоздаётся Wireframe;

Новый wireframe отображается как новая версия

Если изменяется StyleSpecification:

пересоздаются PromptForImageGeneration;

пересоздаётся Wireframe;




Если изменяется DesignProfile:

пересоздаётся PromptForImageGeneration;

FinalImage.никогда не пересоздаётся автоматически, он всегда создаётся только по нажатию на кнопку.

При этом Wireframe должен оставаться неизменным, если изменения касаются только цветов, шрифтов и других визуальных параметров, не влияющих на композицию.
